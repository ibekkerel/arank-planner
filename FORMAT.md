# OpenSchedule 0.5: открытый формат календарно-сетевого графика

Актуальная схема — openschedule.schema.json, версия 0.5. Дополнения и семантика новых полей описаны в RELEASE-0.5.md. Разделы ниже сохраняют историю предыдущих версий; чтение поддерживает 0.1–0.5, запись — 0.5.

## Решение

`.osched` — текстовый UTF-8 JSON, один самостоятельный проект. Канонический контракт — `openschedule.schema.json` (JSON Schema 2020-12) плюс семантические правила ниже. Формат создаётся как открытая спецификация, но не объявляется международным стандартом или сертифицированным аналогом IFC.

Выбор JSON позволяет читать файл без приложения, хранить в Git, сравнивать версии и обмениваться через API. Архивный контейнер с вложениями пока не вводится. JSON сортируется по ключам при сохранении, записи массивов сохраняют порядок. Приложение не сохраняет вычисленные ранние/поздние даты: они воспроизводятся из исходных данных.

## Поля

| Поле | Значение |
|---|---|
| format / version | `OpenSchedule` / `0.4`; другие версии отклоняются |
| id | Стабильная непустая строка идентификатора проекта; рекомендуется UUID |
| name / startDate / currency | Название, дата ISO 8601 `YYYY-MM-DD`, обозначение валюты |
| calendar | IANA timezone; weekdays 1=воскресенье … 7=суббота; holidays — даты исключений |
| activities | id, name, duration (раб. дни), progress (0–100), resource (id или пусто), units (>0), ifcGlobalIds |
| volume / productivity | Необязательные поля: объём ≥0; дневная производительность всей команды >0, если задана, требует объёма |
| links | Уникальный id, from/to, type FS/SS/FF/SF, целочисленный lag в общих рабочих днях |
| resources | id, name, capacity >0, dailyRate ≥0 за единицу ресурса в рабочий день |
| baseline | Объект: id работы → start/finish в рабочих смещениях от текущего начала |

Все поля, кроме volume/productivity/parent/volumeUnit, обязательны для чтения 0.2. Величины конечны. Длительность и лаг ограничены 100000 рабочими днями. Объём можно задать самостоятельно. Производительность требует объёма; отношение не больше 100000. Идентификаторы уникальны в пределах своей коллекции. Связи ссылаются только на существующие работы; назначения — на существующие ресурсы. Граф ацикличен, даже для SS/FF/SF. Изменение начала проекта сдвигает также календарные даты базового плана: baseline хранит относительные смещения, это ограничение 0.2.

## Семантика расчёта

Пусть s — начало, d — эффективная длительность, L — лаг. Каждая связь задаёт нижнюю границу:

- FS: s(B) ≥ s(A) + d(A) + L.
- SS: s(B) ≥ s(A) + L.
- FF: s(B) ≥ s(A) + d(A) − d(B) + L.
- SF: s(B) ≥ s(A) − d(B) + L.

Начало любой работы ≥0. Финиш проекта — максимум s+d. Обратный проход ограничивает финиш каждой работы финишем проекта. Полный резерв = позднее начало − раннее начало. Не следует переносить этот расчёт на разные календари без отдельной модели времени.

Шкала — целые рабочие дни общего календаря, не часы и не секунды. Работы непрерывны в рабочей шкале. Нулевые длительности — вехи, ресурсы в них не потребляются. Перегрузки считаются по полуинтервалам, поэтому передача ресурса на границе не создаёт ложного конфликта.

## Совместимость и развитие

Неизвестные поля, в том числе во вложенных объектах, отклоняются, чтобы исключить их молчаливую потерю при пересохранении. Плагинов и расширений в 0.2 нет. Будущие версии требуют явной миграции; перед миграцией сохраняется исходный файл. Эту спецификацию нужно стабилизировать на независимых реализациях и наборах conformance-тестов.

MSPDI (Microsoft Project XML) — предпочтительный первый адаптер обмена, но это схема Microsoft. IFC — стандартизованный язык BIM, который уже содержит IfcWorkSchedule, IfcTask, IfcTaskTime и IfcRelSequence; его целесообразно использовать для привязки графика к модели и 4D. IFC не принят здесь как единственное внутреннее хранилище всех будущих ресурсных, финансовых и вероятностных моделей.

Будущие адаптеры должны выдавать отчёт: какие календари, лаги, назначения, ограничения, факты, стоимости и пользовательские поля перенесены, преобразованы или потеряны. Файл без проверенного обратного переноса нельзя объявлять совместимым. Для Spider нужен экспорт XML/CSV/XER, реальный тестовый файл и согласование семантики. Чтение его закрытого формата не обещается.

## Изменения 0.2: сущности и иерархия

`activities[].kind`: `task` — задача, `milestone` — веха, `summary` — суммарная задача. Необязательный `parent` ссылается на суммарную задачу. Пустая строка не используется: отсутствие родителя обозначается отсутствием поля. Циклы и отсутствующие родители отклоняются.

Веха имеет нулевую длительность. Суммарная задача не имеет собственной длительности и вычисляется как диапазон от самого раннего начала до самого позднего завершения вложенных задач, включая вложенные суммарные. Вехам и суммарным задачам нельзя назначать ресурс, объём и производительность. Суммарные задачи не добавляют длительность и стоимость проекта. Их резерв в этой версии — минимальный резерв дочерних элементов; это агрегированный показатель, не самостоятельный CPM-резерв операции. Пустая суммарная задача отображается с диапазоном [0,0).

Связи разрешены между задачами и вехами. Связи с суммарными задачами отклоняются: связывать нужно элементы внутри них. В интерфейсе: ФС = FS, СС = SS, ФФ = FF, СФ = SF. Лаги целочисленные, в общепроектных рабочих днях; положительный — задержка, отрицательный — опережение. Объёмные лаги, лаги по разным календарям и ограничения на последователя из расширенных моделей Spider не реализованы.

Ресурс остаётся самостоятельной сущностью коллекции `resources`, а не типом строки `activities`.

Чтение поддерживает 0.1 и 0.2. При открытии 0.1 задача с нулевой длительностью становится вехой, остальные — задачами; сохраняется версия 0.2. Старый исходный файл до сохранения не меняется. Для сохранения исходника используйте «Сохранить как». Старое приложение 0.1 не сможет прочитать 0.2. Схема описывает сохранённые файлы 0.2; целостность ссылок и циклы дополнительно проверяет ядро.


## Версия 0.3

Добавлено необязательное `activities[].volumeUnit` — непустая строка единицы физического объёма (м³, м², т, шт. и т. п.). Объём хранится числом JSON; интерфейс принимает десятичную запятую и преобразует её в число. Назначения ресурсов и их `units` не являются единицей физического объёма.

`volume` может существовать без `productivity`: тогда используется явная `duration`. При наличии положительной `productivity` требуется `volume`, длительность вычисляется как ceil(volume/productivity). Перевод единиц и проверка размерности не выполняются. Веха и суммарная задача не имеют `volumeUnit`.

Чтение: 0.1, 0.2, 0.3; запись: 0.3. Прежние пояснения раздела «Изменения 0.2» описывают историю формата; текущая схема относится к 0.3. Новое поле не удаляется при сохранении. Откат файлов для старого приложения не реализован.

Графическое создание связи использует края полос: F→S = FS, S→S = SS, F→F = FF, S→F = SF. Предварительно выбранный тип можно изменить в свойствах до применения. Координаты и путь линии не хранятся в файле; восстанавливаются из расписания и порядка строк.

Поведение Spider при проведении связи мышью с открытием свойств подтверждается журналом изменений: https://spiderproject.ru/support/whn_r.php. Это аналогичный сценарий взаимодействия, а не заявление о полной идентичности функций Spider.


## Версия 0.4 — даты, условия начала и ресурсная выработка

- `activities[].earliestStart` — необязательное целое 0…100000. Нижняя граница начала на рабочей шкале; запрещена для суммарных задач. Прямой проход CPM инициализируется этой границей вместо нуля. Связи могут отложить задачу дальше.
- `unitCatalog[]`: стабильный `id`, `name`, уникальное `symbol`. В задачах `volumeUnit` пока хранит символ, а не id. Приложение обновляет символы назначений при переименовании единицы. Ссылочная целостность дополнительно проверяется ядром.
- `typeCatalog[]`: `id`, `name`, `unitID`, `outputUnitID`. Оба идентификатора ссылаются на `unitCatalog`.
- `resources[].typeID` — необязательная ссылка на тип. `resources[].productivity` — необязательная конечная положительная выработка одной единицы ресурса в рабочий день. Нужен тип ресурса; размерность = символ `outputUnitID` / рабочий день.

Для задачи с объёмом и без явной `activities[].productivity` используется ресурсная выработка × потребность назначения `activities[].units`. Единица объёма должна совпадать с единицей выработки типа; конверсии размерностей нет. Если ресурсной и явной производительности нет, используется явная duration. Вехи и суммарные задачи собственной выработки не имеют. Стоимость и загрузка используют вычисленную длительность, чтобы не расходиться с сетевым расчётом.

Внутренние окончания исключающие: [start, finish). Поле «Окончание» в UI показывает `date(finish - 1)` для ненулевой задачи, а для вехи `date(finish)`. Это не меняет семантику связей FS/FF/SF.

При переносе создаётся отдельная копия модели, рассчитываются оба состояния. Подтверждение связанного переноса не меняет ни лаги, ни топологию; применение возможно только при достижении запрошенного начала. При отмене исходник остаётся нетронутым. Перед применением также проверяется, что модель не изменилась после расчёта предложения.

Сохранение 0.4 всегда включает справочники. Для чтения 0.1–0.3 отсутствующие справочники дополняются стандартными; неизвестные символы старых объёмов добавляются с новыми id. Схема описывает сохранённый 0.4; прежние разделы — история версий. Автоматического отката в старые версии нет.
